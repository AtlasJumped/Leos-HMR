## TOPIC: video-wallpaper

### RECOMMENDATION
Use Smart Video Wallpaper Reborn v2.16.0 (plugin ID `luisbocanegra.smart.video.wallpaper.reborn`) as the sole video-wallpaper engine on all three monitors — it is the only option that is Plasma-6-native, actively maintained through October 2026, lock-screen capable, and fully scriptable through Plasma's own config system. Install `libqt6multimedia6` + `qml6-module-qtmultimedia`, get the plugin from the KDE Store (ID 2139746) to avoid the missing-cmake problem (or `apt install cmake extra-cmake-modules libplasma-dev` and run its install.sh for a system-wide install), set `QT_FFMPEG_DECODING_HW_DEVICE_TYPES=cuda` via the plugin's Advanced tab so the 5090s' NVDEC does the decoding, and set `PauseMode=3` so video never pauses. Drive the "mode" command as one shell script: (1) `qdbus6 ... evaluateScript` with the KDE-canonical `desktops()` loop, filtering by `d.screen`/`screenGeometry()` to write a per-monitor `VideoUrls` JSON (this applies live — no plasmashell restart); (2) `kwriteconfig6` on `kscreenlockerrc` (`[Greeter] WallpaperPlugin` + nested `[Greeter][Wallpaper][<id>][General] VideoUrls`) for the lock screen; (3) `plasma-apply-colorscheme`, `plasma-apply-cursortheme`, `plasma-apply-desktoptheme` for the rest of the re-skin; browser and dashboard theming need their own hooks (Firefox follows the system scheme; the kiosk dashboard can watch the same mode state file). Do not use mpvpaper (its maintainer explicitly does not support KWin — plasmashell's opaque desktop covers it) and do not adopt the archived catsout plugin; its successor waywallen (v0.4.4, Oct 2026) is worth bookmarking only if you later want Wallpaper Engine "scene" shader wallpapers, since for plain video it needs plasmashell restarts, a VA-API shim on NVIDIA, and offers no cleaner scripting. One plan correction: login-screen video requires Plasma Login Manager, so with GDM the chain is video-from-lock-screen-inward only — either accept a static GDM greeter or switch display managers.

## TOPIC: mode-theming

### RECOMMENDATION
Build the mode system as a bash orchestrator ("mode <women|dogs|scifi|fantasy>") around verified Plasma 6.6 primitives rather than any single theming framework. Always-on video: install luisbocanegra's smart-video-wallpaper-reborn (v2.16.0, actively tracking Plasma 6.5-6.7) with the FFmpeg+CUDA backend — it is the only maintained in-plasmashell video wallpaper (the catsout Wallpaper Engine plugin in the current plan was archived June 2026), it covers desktop AND lock screen, and its pause-on-fullscreen/screen-off conditions keep the 240Hz desktop cheap; render loops at native 3440x1440 per monitor (not 4K 16:9) via ffmpeg or the ComfyUI/5090 pipeline. Per mode, package the static identity (Catppuccin flavor color scheme from the live catppuccin/kde repo, icons, cursor, Klassy decoration — Klassy's current branch requires exactly Plasma 6.6) as four hand-written Plasma/LookAndFeel packages installed with kpackagetool6 and applied in one shot with plasma-apply-lookandfeel -a (appearance-only by default, no logout, and more reliable than Plasma 6.6's new-but-buggy GUI theme creator). The script then drives what look-and-feel can't: per-screen VideoUrls via org.kde.PlasmaShell evaluateScript (the exact mechanism plasma-apply-wallpaperimage uses, verified in source), kscreenlockerrc via kwriteconfig6 (no root), Konsole via a D-Bus loop over org.kde.konsole* sessions calling setProfile, Kando by rewriting menuTheme/menuThemeColors in ~/.config/kando/config.json (hot-reloaded live; install Kando 3.0.0 from the official .deb), panel accents via panel-colorizer's documented D-Bus preset switching (v8.0.0), and the Glance dashboard via its own theme reload. Do the GTK/flatpak work once, not per mode: keep GTK style = Breeze so kde-gtk-config auto-follows each mode's colors, add the flatpak xdg-config overrides, and accept that libadwaita apps only tint. Leave the GDM login screen out of the mode system (it's GNOME-themed and root-owned); if a video login screen is wanted, make a one-time switch to Plasma Login Manager (optional in 6.6, supports the same video plugin via /etc/plasmalogin.conf). Prerequisites are light — ffmpeg, the four packages above, and the catppuccin repos; no cmake/Rust/Go unless building Klassy from source. Before wiring all four modes, test two things once by hand, as they rest on medium-confidence sources: the evaluateScript write of VideoUrls, and the exact [Greeter] plugin keys kscreenlockerrc uses for the video plugin (set it once in System Settings and diff the file).

## TOPIC: browser-mouse-flair

### RECOMMENDATION
For the one-shot `mode` command on this exact box, build on what is verified live-switchable and avoid everything restart-bound. Wallpaper video: install Smart Video Wallpaper Reborn (KDE Store 2139746) plus qt6-multimedia's FFmpeg backend, set the NVIDIA FFmpeg+CUDA decode backend and pause condition 'never', one 3440x1440 video per containment on DP-1/DP-2/DP-3; the mode script swaps video paths through `qdbus org.kde.plasmashell /PlasmaShell evaluateScript` and sets the Plasma look via `plasma-apply-colorscheme`/`plasma-apply-lookandfeel`. - [high] chrome-theme-policy-live: Chrome's BrowserThemeColor enterprise policy generates and applies a full browser theme from one hex color and supports dynamic refresh — no browser restart needed.
- [high] chrome-policy-file-watch-linux: Chrome on Linux watches its policy directories with a file watcher and reloads policies immediately when a JSON file changes, so a mode script's policy write re-skins running Chrome windows within seconds.
- [high] chrome-dark-mode-portal: Chrome >=114 follows the system light/dark preference on Linux live via the org.freedesktop.appearance color-scheme key of xdg-desktop-portal (SettingChanged subscription), so switching the Plasma color scheme flips Chrome UI and prefers-color-scheme sites without restart.
- [medium] chrome-force-dark-flag: --force-dark-mode is a launch-time flag (needs relaunch), and the chrome://flags 'Auto Dark Mode for Web Contents' inverter also requires a browser restart — neither is suitable for live mode switching.
- [medium] chrome-no-theme-extension-api: Chrome has no chrome.theme extension API: an unpacked extension cannot set or switch the browser theme at runtime; themes are static packaged extensions applied on install, so scripted Chrome re-theming must go through enterprise policy (or per-mode profiles).
- [high] firefox-theme-api-live: Firefox's browser.theme.update() lets an installed WebExtension (manifest 'theme' permission) swap the entire browser theme instantly at runtime, even per-window — the best live Firefox re-theming hook for a mode script.
- [medium] firefox-policies-restart: Firefox reads policies.json at startup only — force-installing a static theme XPI via ExtensionSettings works, but swapping it per mode requires a browser restart, so it is a provisioning tool, not a live-switch mechanism.
- [medium] firefox-userchrome-no-hot-reload: userChrome.css still requires toolkit.legacyUserProfileCustomizations.stylesheets=true and is loaded only at startup; there is no supported hot-reload, only manual live editing through the Browser Toolbox.
- [medium] firefox-color-authoring: Firefox Color (mozilla/FirefoxColor, color.firefox.com) is a live theme editor extension — good for designing each mode's palette and exporting it, but not a scriptable switcher.
- [medium] browser-profiles-fallback: Per-mode browser profiles with preinstalled themes (chrome --profile-directory='Mode-X', firefox -P mode-x) work on any browser version with zero policy machinery, but only new windows get the mode theme — already-open windows of another profile keep theirs.
- [medium] firefox-dark-portal-unreliable: Firefox's live following of a Plasma Wayland dark/light switch is historically flaky (portal restarts, relogin, FF141 regression reports), so a mode script should not depend on it — drive Firefox explicitly via the theme API.

## TOPIC: perf-power

### RECOMMENDATION
Use plasma-smart-video-wallpaper-reborn (v2.16.0, actively maintained, Plasma 6 native) as the video wallpaper layer, with blur OFF, pause-on-maximized/fullscreen ON, pause-on-screen-off ON, and 3440x1440-native HEVC loops at 24-30fps encoded with hevc_nvenc — do not use 4K/60 sources, since scaling and the plugin's known Qt Multimedia overhead (2-3x direct playback GPU util on a 4090 with the same ultrawides, issue #18) are the dominant costs, not NVDEC decode itself. Budget honestly: this triple-240Hz setup will likely hold the display GPU at ~50-90W idle with VRAM pinned regardless of wallpaper (anecdotal but consistent 5090 reports; reviews show 30-46W single-monitor), and continuous playback adds roughly 20-35W more (PCGH measured 52-65W for UHD video on a 5090) — call it an extra ~250-700kWh/yr versus static wallpaper depending on pause discipline. Abandon the idea of decoding the wallpaper on the second 5090: the plugin's GPU selector only separates different backend types (vaapi/cuda/qsv) and cannot split two CUDA cards, and mpv's --cuda-decode-device doesn't apply to its Vulkan path; instead pin the entire desktop (KWin + all three monitors + decode) to GPU0 via KWIN_DRM_DEVICES=/dev/dri/by-path/... and leave GPU1 with zero display/compositor state for AI jobs, monitored via Beszel with GPU_COLLECTOR=nvml (the default nvidia-smi collector can block low-power states) plus an nvidia-smi dmon/query-gpu tile showing pstate, power.draw, clocks.mem and utilization.decoder per GPU. For mode switching, build the "mode" command on plasma-apply-colorscheme + plasma-apply-cursortheme and the plugin's v2.15 dark/light per-mode videos (or qdbus evaluateScript for N modes) — one command re-skins scheme, cursor and all three videos; note the GDM login screen cannot carry the video (lock screen can). Two live risks to test before committing: the open NVIDIA UVM suspend-deadlock bug with hardware-decoded wallpapers on a 5090 (issue #281 — test systemctl suspend with wallpaper active), and frame pacing on Plasma 6.6.6, which still lacks NVIDIA triple buffering (restored only in 6.7.3 — upgrade when Ubuntu ships it). Fullscreen games on one monitor should keep per-output direct scanout despite wallpapers elsewhere (medium confidence), and the pause-on-fullscreen option removes the contention anyway. Finally, measure before/after on this exact box — 5-minute power.draw/pstate averages across static, paused, playing, and gaming states — because every multi-monitor idle number in the wild is configuration-dependent and much of the public data is anecdotal.
