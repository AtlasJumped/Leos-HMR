## TOPIC: frigate-core

### RECOMMENDATION
Use Frigate 0.18.x. It is still the right choice here and active (0.18.0 on 12 Sep 2026, MIT licence). Pin the image to a version tag with the -tensorrt suffix (for example ghcr.io/blakeblackshear/frigate:0.18.0-tensorrt; the 0.17-style version tag is confirmed, so verify this tag exists) rather than 'stable'.

Plan for Aletheon:
1. Deploy with compose. Use a deploy.resources.reservations.devices block with driver nvidia, device_ids ['1'] (or the GPU UUID) and capabilities [gpu]. Set detectors: {onnx: {type: onnx}}, with ffmpeg.hwaccel_args: preset-nvidia, shm_size '1gb', a 1 GB tmpfs at /tmp/cache, /config on the NVMe pool and /media/frigate on tank. Publish 127.0.0.1:5000 for the scrub job and the perception bridge (loopback-only, unauthenticated admin) and 127.0.0.1:8971 behind Caddy for the browser UI. Confirm with 'docker exec frigate nvidia-smi -L' that exactly one GPU is visible (the image sets NVIDIA_VISIBLE_DEVICES=all). Use the YOLOv9-s 320 ONNX export (model_type yolo-generic) first. If detection hangs ('Detection appears to be stuck'), which was the Blackwell failure mode on 0.17 and one user still reported on a 5070 on 2 Oct 2026, switch to YOLO-NAS (model_type yolonas), which skips the CUDA-graph runner. Run it for a week before trusting it. Nobody has reported a 5090 with Frigate that I could find, but the 5060 Ti (same sm_120) is the maintainers' test card for 0.18.

2. Recording policy. Because a person sitting still stops counting as an active object, go with the hybrid: record.continuous.days 1-2 (about 350 GB/day for 4 high-bitrate streams, fine on tank), record.motion.days 0-2, and alerts retain days 14 with mode all and 10 s pre/post capture. Add one loitering zone per camera over the room. Set detect.enabled: True explicitly. If you want strictly 'person only' recording, set continuous 0 and motion 0 and rely on alerts (person) plus the loitering zone. That natively discards no-person footage, and the daily scrub then only needs to handle guests.

3. Identity. Enable face_recognition with model_size large on the GPU (or small on CPU first), set the camera's detect stream to 1080p-1440p, and enrol 20-30 real captures of Leo from the actual cameras. Do not expect faces to be visible every time: events where the face is never seen keep sub_label null. Treat null as 'unidentified, keep', and delete only events where a different enrolled guest was recognised and no Leo/unknown person overlaps. There is no native person re-ID. A custom person classification model (attribute) could add a clothing-based signal but it is fragile. Place cameras at eye level at doorways and chokepoints. Mount, resolution and IR behaviour matter more than model size.

4. Scrub job. Authenticate to the loopback port, list person events per camera for the previous day (GET /api/events?labels=person&after=&before=), build padded keep intervals (>= 20 s), merge them, then delete the gaps with DELETE /api/recordings/start/{s}/end/{e}?cameras=<cam> (0.18+, admin). Do not use DELETE /api/events for freeing space. It leaves the video. Follow with POST /api/media/sync and dry-run for a week while logging intervals.

5. Perception for Claude. Pull GET /api/{camera}/latest.jpg?height=720 and /api/events?in_progress=1 on demand. For push events, run a local mosquitto broker on 127.0.0.1 and a small bridge from frigate/events, frigate/reviews and tracked_object_update into your events.json/SSE system. Only use the community Frigate MCP servers after auditing their code.

6. Camera purchase. The Amazon item could not be opened. Accept it only if it has local RTSP (or http-flv) with separate main and sub streams, ONVIF, H.264 (H.265 is OK), PoE wired, no mandatory cloud, usable resolution of 4MP or more with a 1080p+ second stream, good low-light/WDR, and a lens covering the room depth. Avoid Wi-Fi, battery and cloud-only cameras (Ring, Arlo, Blink, Nest, stock-firmware Wyze). Disable audio recording, and keep the cameras off the internet, optionally on their own subnet on the idle 10GbE port.

7. Operations. Keep Frigate patched (several security advisories in 0.16.2-0.17.2) and loopback-only. Watch for 0.18.x patches. Test sub_label persistence, tracked-object splitting and the null-sub_label case with a real day of footage before enabling any automatic deletion.

### FINDINGS
- [high] frigate-version-and-release-timeline: As of 2026-10-11 the latest stable Frigate is v0.18.0 (published 12 Sep 2026); the previous line is 0.17.x (0.17.0 on 27 Feb 2026, 0.17.1 on 22 Mar, 0.17.2 on 28 Jun). I found no 0.18.1.
- [high] release-0.18-notable: 0.18.0 is the first release the maintainers describe as officially supporting NVIDIA 50-series (Blackwell), and it also brings API and config changes that matter for a scrub job.
- [high] release-0.16-0.17-notable: 0.16 introduced face recognition and removed the native TensorRT detector for desktop NVIDIA GPUs. 0.17 split continuous and motion retention and added custom object and state classification.
- [high] project-health: Frigate is active, MIT-licensed and has a large community, though it has had frequent security advisories. It is not abandoned.
- [medium] alternatives-brief: Frigate remains the best fit for a Linux, local-only, GPU-detection, face-capable NVR. The alternatives each fall short on one requirement.
- [high] record-schema-0.18: In 0.17+/0.18 the recording schema is tiered: record.enabled, record.continuous.days, record.motion.days, and record.alerts / record.detections each with pre_capture, post_capture and retain {days, mode}, where mode is all, motion or active_objects.
- [medium] record-only-when-motion-or-person: There is no single 'record only when person' switch. Set continuous.days 0 and motion.days 0 so nothing is kept without an object, and keep recordings only through alerts (person by default). Use motion.days > 0 for 'motion only'.
- [high] review-alerts-vs-detections: Alerts are person and car objects by default; detections are everything else tracked. Both can be narrowed by review.<tier>.labels and review.<tier>.required_zones.
- [medium] stationary-person-recording-gap: Risk: a person sitting still (desk, couch) is treated as a stationary object. That ends review items and does not count as 'active' for active_objects retention. A loitering zone and mode: all are needed to keep the whole sitting period.
- [high] pre-post-capture: pre_capture and post_capture default to 5 s each (max 60 s), are set separately for alerts and detections, and operate on 10 s segments, so actual lead and lag vary by up to about 10 s.
- [high] face-recognition-how-it-works: Built-in face recognition runs locally on the detect stream. It first needs a 'person' tracked object, finds a face in the person crop, embeds it with FaceNet (small, CPU) or ArcFace (large, GPU recommended) and matches against a trained library.
- [high] face-recognition-config-keys: The face_recognition keys are enabled, model_size, detection_threshold, min_area, unknown_score, recognition_threshold, min_faces, save_attempts, blur_confidence_filter and device. The documented min_area default conflicts: 750 on the feature page, 500 in the reference config.
- [high] face-recognition-training-flow: Training is done in the web UI (Face Library, Add Face wizard, Train tab). Docs advise a few clear front-facing photos first, then dozens of varied real captures. Diversity beats volume, and bulk uploads cause over-fitting.
- [medium] face-sublabel-aggregation: The sub_label is published only when a per-object weighted average of face attempts (weighted by face area and score margin) reaches recognition_threshold with at least min_faces non-unknown attempts. Per-object attempts are capped, so a person who never presents a usable face never gets a name.
- [medium] face-sublabel-persistence-on-event: Once published, the recognised name is stored on the tracked object and written to the Event row (sub_label plus data.sub_label_score), so it applies to that whole tracked-object event. It does not carry to a new tracked-object ID created when the person leaves and re-enters view or the track is lost.
- [medium] face-recognition-real-world-limits: Indoor face recognition works only when a sharp, roughly frontal face of enough pixels appears in the detect stream. Distance, compression, motion blur, IR/grayscale and angle all degrade it, and Frigate publishes no accuracy figures.
- [medium] face-never-visible: If no face is ever detected in the person crop, no recognition attempt happens, the event keeps sub_label = null, and Frigate cannot tell Leo from a guest for that event.
- [medium] object-classification-custom: 0.17+ ships user-trained object classification (a MobileNetV2 model) that can set a tracked object's sub_label or an attribute. It could be trained on 'person' crops (for example Leo vs guest vs none) as a face-independent signal, but it is appearance (clothing) based and fragile.
- [medium] person-reid-not-supported: Frigate has no native person re-identification (appearance-based identity across tracks or cameras). Related upstream requests were closed as not planned.
- [medium] blackwell-5090-detector-status: Frigate 0.18.0 officially supports 50-series (Blackwell) GPUs through the ONNX detector in the -tensorrt image, but I found no confirmed RTX 5090 report. Blackwell stability on 0.16 and 0.17 was poor and some reports persist.
- [high] detector-image-and-docker-flags: Use image ghcr.io/blakeblackshear/frigate:<version>-tensorrt (or stable-tensorrt) with detectors: {onnx: {type: onnx}}. The old native TensorRT detector (type: tensorrt, YOLO_MODELS env) exists only for Jetson (-tensorrt-jp6). GPU passthrough uses a compose deploy reservation (or --gpus).
- [medium] gpu-selection-pin-to-gpu1: Pin Frigate to GPU1 (the compute GPU) with device_ids in the compose reservation. The container then sees one GPU as index 0. If both GPUs are visible, detector/enrichment/ffmpeg indices must be set explicitly.
- [medium] detector-models-and-speed: Start with YOLOv9-s at 320x320 (model_type: yolo-generic) on the ONNX detector. Keep YOLO-NAS (model_type: yolonas) as a fallback because it bypasses the CUDA-graph runner that hung on Blackwell in 0.17. Inference is single-digit milliseconds on a modern RTX.
- [medium] ffmpeg-nvidia-decode: For NVDEC decode set ffmpeg: {hwaccel_args: preset-nvidia} (global or per camera). The default is 'auto'. Docs do not mention Blackwell NVDEC explicitly, but the preset auto-selects the codec profile.
- [high] api-list-events: GET /api/events accepts after/before (epoch seconds), camera(s), label(s), sub_label(s), attributes, zone(s), has_clip, has_snapshot, in_progress, min/max_score, limit (default 100), sort, timezone and more.
- [medium] api-event-fields: Each event object has id, label, sub_label (string or null), camera, start_time, end_time (null while in progress), has_clip, has_snapshot, zones, retain_indefinitely, plus a free-form data object that holds top_score, score, sub_label_score and attributes.
- [high] api-delete-events-frees-no-video: DELETE /api/events/{id} and bulk DELETE /api/events (body {event_ids:[...]}) remove only snapshot files and DB rows. They do NOT delete recording video, so they do not free meaningful disk.
- [high] api-delete-recordings-time-range: New in 0.18: DELETE /api/recordings/start/{start}/end/{end}?cameras=cam1,cam2&keep=motion|object|audio (admin) deletes recording files from disk and their DB rows for every segment overlapping the range. This is the endpoint that actually frees disk.
- [high] api-delete-review-items: POST /api/reviews/delete (admin) with body {ids:[review_ids], reviewed?} deletes the recording files and rows overlapping each selected review item, plus the review rows. It does not delete exports.
- [high] api-auth-model: Port 8971 requires login (JWT cookie or Authorization: Bearer). Port 5000 is unauthenticated and treated as anonymous admin. Frigate has no separate API keys. A local script either POSTs /api/login on 8971 or talks to 127.0.0.1:5000.
- [medium] perception-interface-for-claude: For a Claude-facing 'eyes' interface, Frigate offers HTTP pull endpoints (latest frame, event snapshots, stats) and MQTT push topics (events, reviews, face updates, per-camera object counts). There is no documented SSE or WebSocket push for third parties.
- [low] scrub-job-design: A daily scrub is feasible with the 0.18 API: list person events and sub_labels per camera, compute 'keep' intervals, then delete the complement by DELETE /api/recordings/start/{s}/end/{e}?cameras=<cam>. Delete the gaps between kept intervals, never the events themselves, and default unknowns to keep.
- [medium] performance-resources-4-cameras: Four cameras need roughly 150-1000 MB of shm_size depending on detect resolution, and CPU/RAM needs are small for this hardware. Frigate publishes no official CPU/RAM figures for 4 cameras.
- [medium] camera-compatibility-checklist: Any camera usable with Frigate needs a local RTSP (or HTTP-FLV) stream, ideally two simultaneous streams, stable H.264/H.265, and no mandatory cloud. Wi-Fi, battery and cloud-only cameras (Ring, Arlo, Blink, Nest, most Wyze on stock firmware) are poor fits.
- [low] network-and-host-layout: Four PoE cameras fit easily on the existing 1GbE. A dedicated camera network on the idle 10GbE port is optional hardening, not a requirement.
- [high] stale-info-flags: Much online Frigate material is stale for 0.18: the old TensorRT detector, record.retain/events.retain, sync_recordings, DELETE /api/export, 'Frigate has no face recognition', and pre-0.18 Blackwell warnings.
- [high] research-limits: This research read the official v0.18.0 repository docs and source, not the rendered docs site, and found no direct RTX 5090 + Frigate report.

## TOPIC: camera-hardware-network

### RECOMMENDATION
For Aletheon: run Frigate 0.18.x (pin the exact tag; 0.18.0 stable shipped 12 Sep 2026) in Docker bridge mode with ports published on 127.0.0.1, using the -tensorrt image and the ONNX detector plus preset-nvidia decode. Blackwell worked poorly on 0.17 and had residual stall reports as recently as 2 Oct 2026, so test it and keep an OpenVINO/CPU detector config as fallback. Frigate is still the right NVR. It keeps person clips and deletes the rest natively, so you don't need a daily scrub script. Set continuous to 1-3 days as a safety net, and set person alerts and detections to 30-60 days with mode motion. It cannot yet be confirmed to keep only clips of you while dropping guests, because face-recognition sub_labels aren't documented as usable in retention.

Cameras: buy 4 wired PoE fixed cameras with a 5MP-or-lower H.264 main stream and a usable sub-stream. Skip Wi-Fi, battery, cloud, Ring/Arlo/Blink/Nest/Wyze and Eufy, and skip PTZ unless it is a Dahua/EmpireTech unit.
- Best price/availability: Reolink RLC-520A or RLC-510A (about $45-70; use http-flv or H.264, CBR, I-frame interval equal to fps).
- Best Frigate behavior: EmpireTech/Dahua or Amcrest, about $100-150 (Dahua OEM). US availability and FCC/NDAA status are in flux, so check stock and returns first.
- Cheap alternative: TP-Link VIGI C230I Mini, a 3MP PoE dome (main stream H.264, Smart Coding off). Avoid Tapo, which is Wi-Fi.
- Treat all model names and prices as approximate (low confidence). I couldn't open any vendor pages or the Amazon link. Paste the product title or model and I'll run the checklist on it.
- Buy ONE camera first and test it. Check that the RTSP URL plays in VLC or ffprobe, that main and sub streams both work, that H.264 is available, and that it stays up for 24 hours with no internet. Then buy the other three.

Switch and cabling: use an 8-port gigabit switch with all ports PoE+ and about 120 W or more (e.g. TL-SG1008MP class), unmanaged or web-smart with no cloud management. Do not buy a 2.5G/10G switch; four cameras need only about 10-35 Mbps. Avoid '8-port' switches where only 4 ports give PoE. Use solid-copper Cat5e/6, never copper-clad aluminum. Put the switch and PC on a UPS.

Network isolation:
- Cable the switch directly to the AQC113 port and nothing else.
- In netplan, give that NIC a static address (suggest 10.77.77.1/24) with no routes, gateway or DNS, plus `optional: true`, `link-local: []` and a per-device `renderer: networkd`. Verify with `netplan try`, and check that NetworkManager ignores it.
- Use dnsmasq for DHCP only (`port=0`, `bind-dynamic`, `interface=cam0`, empty router and DNS options, option 42 pointing at the PC, reservations by MAC).
- Use chrony for time (`binddevice cam0`, `allow 10.77.77.0/24`, `local stratum 10`).
- Docker turns on ip_forward and the FORWARD drop policy by default, so true "no forwarding" isn't possible. Instead use the separate nftables table `inet camlan` from the findings, which drops everything from the cameras except DHCP, NTP and ping to the PC, plus any forwarding from cam0. I only syntax-checked it with `nft -c`; I haven't tested it on a live network.
- Never run `flush ruleset` (it would wipe Docker's tables), and never use NetworkManager's "Shared" mode.
- Provision and patch each camera first on a temporary internet-connected network, then move the switch to cam0.

Hardening and storage:
- Per camera: unique alphanumeric password, a separate stream user, and P2P, UPnP, cloud and DDNS off.
- Firmware only from the vendor's own site.
- Passwords go into Frigate via FRIGATE_* environment variables in an env_file outside git.
- Storage: four cameras at about 4 Mbps main-stream is about 173 GB/day, or 5.2 TB per 30 days if recorded continuously. Person-only retention is roughly 0.5-2 TB per 30 days. Put recordings on tank in a dataset with no auto-snapshots, and keep the DB and /config on NVMe.
- Privacy: avoid continuous audio recording and cameras in bathrooms or guest sleeping areas.

### FINDINGS
- [high] research-access-limits: Vendor pages (reolink.com, amcrest.com, tp-link.com, ui.com), docs.frigate.video and most review sites were unreachable from this sandbox, so primary-source verification was limited to GitHub (Frigate docs on the dev branch, releases, discussions), Ubuntu docs, systemd/dnsmasq/chrony/netplan/Docker docs-in-GitHub; vendor model specs and prices are secondary and approximate.
- [high] frigate-release-status: Frigate is actively maintained: stable v0.18.0 was released 12 Sep 2026 (after 0.17.0 on 27 Feb 2026, 0.17.1 on 22 Mar, 0.17.2 on 28 Jun); the repo is MIT-licensed with ~36.5k stars, and the name/brand are trademarks of Frigate, Inc.
- [medium] nvr-alternatives-2026: Frigate remains the best fit for 'GPU object detection + keep only person clips'; the alternatives are either maintained but weaker for this goal (Viseron, Scrypted, ZoneMinder), lack object detection (Moonfire), effectively dormant on GitHub (Shinobi), or Windows-only (Blue Iris).
- [high] frigate-native-keep-person-retention: Frigate can implement 'keep clips where a person appears, delete the rest' natively through tiered retention (record.continuous / record.motion / record.alerts / record.detections) with person as the default alert label, so no separate daily scrub script is needed.
- [medium] cameras-need-not-be-motion-detecting: For a Frigate design the cameras should be always-on RTSP streamers; on-camera motion detection is unnecessary, and PIR/battery 'motion-triggered' cameras are incompatible with 24/7 streaming.
- [medium] frigate-blackwell-rtx50: Frigate 0.17 had a reproducible detector hang on Blackwell (sm_120) GPUs, 0.18 is the first release claiming RTX 50-series support, but residual 'Detection appears to be stuck' reports on 50-series cards persisted as late as 2 Oct 2026, so the 2x RTX 5090 host should be treated as 'supported but test before trusting'.
- [high] frigate-official-camera-guidance: Frigate's own hardware docs recommend Dahua, then Hikvision, then Amcrest (Amcrest = rebranded lower-end Dahua), want H.264 video + AAC audio and multiple sub-streams, say larger sensors beat higher resolution especially at night, say Wi-Fi cameras are not recommended, and say to stick to 5MP or lower for Reolink.
- [high] reolink-frigate-status: Reolink PoE cameras of 5MP or lower (RLC-510A/520A class) work well with Frigate when pulled via http-flv (H.264) with CBR and I-frame interval = fps, but Reolink's RTSP implementation is called 'flawed' by a Frigate maintainer, 8MP+ models are less reliable, and Reolink PTZs cannot be used with Frigate autotracking.
- [high] rtsp-url-formats-verified: Documented RTSP/stream URL formats: Dahua/Amcrest rtsp://U:P@IP/cam/realmonitor?channel=1&subtype=0 (main) and subtype=1 (sub); Hikvision/Annke rtsp://U:P@IP/streaming/channels/101 (main) and /102 (sub); Tapo rtsp://U:P@IP:554/stream1 (main) and /stream2 (sub); Eufy indoor rtsp://U:P@IP:554/live0 (reported, per-model).
- [medium] dahua-hikvision-amcrest-us-availability-and-ndaa: Dahua/EmpireTech/Amcrest (Dahua OEM) and Hikvision hardware remain the technically best-regarded for Frigate but carry 2026 regulatory/supply risk: NDAA s.889 bars federal use (incl. relabeled OEM units), the FCC has authorized no new Hikvision/Dahua models since Nov 2022, and secondary sources report a June 2026 FCC action extending import/marketing bans to previously authorized units (privately owned installs unaffected).
- [medium] camera-vulnerabilities-2025-2026: Dahua and Hikvision cameras have actively exploited pre-auth vulnerabilities in 2025-2026 (Dahua CVE-2025-31700 ONVIF stack overflow and CVE-2025-31701 RPC upload; Hikvision CVE-2021-36260 still mass-scanned; Check Point documented Iran-linked exploitation of five old Hikvision/Dahua CVEs in Mar 2026), which makes network isolation plus firmware patching mandatory for those brands.
- [low] indoor-model-shortlist: Best-supported wired indoor-capable picks as of Oct 2026 (approximate prices, verify): Reolink RLC-520A (5MP PoE dome, ~$45-70), Reolink RLC-510A (5MP PoE bullet, ~$47-60), EmpireTech/Dahua IPC-T5442T-ZE (4MP varifocal PoE, ~$100-150), Amcrest IP5M-T1179EW-AI (5MP PoE turret, $99.99), TP-Link VIGI C230I Mini (3MP PoE dome, ~US$45-65); for indoor PTZ with PoE only Dahua/EmpireTech PTZ units are consistently reported to work with Frigate.
- [high] substream-detect-resolution: For detection a 640x360 to 1280x720 sub-stream (5 fps) is sufficient because Frigate crops motion regions and resizes to a 320x320 model; set the detect stream's aspect ratio equal to the main stream's (16:9 main -> 640x360, not 640x480), record the main stream at ~15 fps with a keyframe interval matching fps, and put frame-rate changes in the camera, not Frigate.
- [low] ir-night-vision-fov-indoor: For indoor use choose cameras with larger sensors and controllable IR/white-light (night images will be grayscale under IR, which degrades face recognition), and pick lens FOV by room size (about 2.8 mm for small rooms, 4 mm+ for long rooms).
- [high] ptz-onvif-autotracking-support: Frigate PTZ autotracking works reliably only on Dahua/EmpireTech PTZs; Reolink (incl. TrackMix) and Hikvision-firmware cameras do not work, so buy fixed cameras unless plain ONVIF PTZ control (not autotracking) is enough.
- [low] audio-and-two-way-talk: Local two-way audio through go2rtc/Frigate is unreliable on current PoE cameras (June-Sept 2026 reports of echo/latency on Reolink E1 Outdoor and a Dahua PTZ that stopped working), so treat microphones as record/detect-only and do not buy for talk-back.
- [medium] tapo-tplink-vigi: TP-Link Tapo cameras expose RTSP (stream1/stream2, port 554) and ONVIF and work with Frigate, but Frigate maintainers attribute Tapo C-series dropouts to Wi-Fi, users report overheating/instability under 24/7 streaming, and Tapo setup/NTP depend on the Tapo cloud app; the wired TP-Link VIGI line is the better TP-Link choice.
- [high] unifi-protect-cameras: UniFi Protect cameras (G5 and newer) only expose an RTSPS stream when adopted by a UniFi Protect console (UNVR/Cloud Key/UDM); standalone mode cannot enable it, so they add a console, a Ubiquiti-managed controller and cost to a Frigate-only design.
- [low] wyze-status: Wyze is not a good Frigate camera: official RTSP firmware exists only for legacy V3/Pan V3 and is deprecated, Cam v4 has no confirmed native RTSP, Wyze cameras are Wi-Fi, and the alternative open firmware (Thingino) can brick units and severs the Wyze app.
- [low] eufy-status: Some Eufy indoor cameras (C120/E220/S350 class) offer an app-toggled RTSP stream (reported path /live0), but it is Wi-Fi, has reported 401/authentication and drop-out issues (stream only persists when set to record continuously), and requires Eufy cloud pairing, so it is a workaround not a recommendation.
- [medium] incompatible-cloud-cameras: Ring, Blink, Nest and (effectively) Arlo cameras are incompatible with a local Frigate setup: none offers a usable local RTSP/ONVIF stream, and go2rtc can only reach Ring/Nest/Wyze/Tapo-class devices through their cloud/private protocols, which defeats an internet-isolated camera LAN.
- [medium] amazon-listing-compatibility-checklist: A listing is a good Frigate candidate only if it passes this 30-second test: wired PoE (802.3af/at) + explicit 'RTSP' and 'ONVIF (Profile S/T)' + main and sub streams + H.264 (or H.265 w/ H.264 option) + 'no subscription / local storage' + from a known brand with downloadable firmware; any red flag below should end the evaluation.
- [high] poe-vs-wifi: Wired PoE is the correct choice for four 24/7 Frigate cameras: Frigate docs say Wi-Fi streams are less reliable, multiple Frigate threads trace Wi-Fi camera dropouts to the radio link, and one Cat5e/6 cable per camera also removes separate power supplies.
- [medium] poe-switch-selection: Buy an unmanaged or web-smart (non-cloud-managed) gigabit switch with at least 5-8 PoE+ ports and ~100-130 W budget; 2.5G/10G uplink is unnecessary because four cameras produce only ~10-35 Mbps; beware '8-port' switches where only 4 ports supply PoE (e.g. TP-Link TL-SG1008P: ports 1-4 PoE, 64 W total).
- [medium] isolated-camera-lan-netplan: Dedicating the unused AQC113 10GbE port to a camera-only subnet is done with one netplan file: static address on that NIC, no routes/gateway/nameservers, optional: true, link-local disabled, and a per-device renderer: networkd so Ubuntu Desktop's NetworkManager ignores it (test with netplan try).
- [high] camera-dhcp-dnsmasq-or-static: Cameras can get addresses either from a DHCP-only dnsmasq bound to the camera NIC (DNS disabled with port=0, no router and no DNS options handed out) or from static IPs set in each camera; DHCP with MAC reservations is easier to recover after a factory reset.
- [high] camera-ntp-without-internet: Cameras can keep correct time with no internet by pointing their NTP-server field (or DHCP option 42) at chrony on the PC, restricted to the camera NIC with 'binddevice cam0', 'allow 10.77.77.0/24' and 'local stratum 10'; cameras with no NTP-server field (Tapo-class, cloud time) will drift or reset at reboot.
- [high] docker-forwarding-vs-no-ip-forward: 'No IP forwarding' is not achievable on a host running Docker's default iptables backend, because Docker enables net.ipv4.ip_forward at daemon start; isolation must therefore come from the cameras having no gateway plus explicit drop rules on the camera interface (the experimental nftables backend in Docker 29 does not enable forwarding for you).
- [medium] nftables-camera-lan-guard: A separate 'inet camlan' nftables table can drop all camera-originated traffic except DHCP/NTP/ping to the PC and block any forwarding from the camera NIC (while still allowing replies to Frigate's own connections), and it coexists with Docker's rules as long as nothing runs 'flush ruleset'.
- [medium] isolation-pitfalls-and-provisioning: With no gateway the cameras' cloud/P2P/DDNS/UPnP features will fail silently or noisily (offline status in vendor apps, retry loops, possible LED/voice 'offline' prompts) but RTSP/ONVIF recording continues; firmware updates become a manual download-from-vendor and upload-via-web-UI task, and the right order is to provision and patch each camera on a temporary internet-connected network first, then move the switch to the isolated NIC.
- [low] direct-nic-vs-vlan-iot-ssid: A cable-direct camera NIC is a stronger isolation design than a router VLAN or IoT/guest SSID because there is physically no gateway to misconfigure, no consumer-router VLAN support is needed, and no Wi-Fi client-isolation quirks block the PC from reaching cameras; its costs are one cable run from the switch to the PC and a PC that is a single point of failure.
- [medium] camera-hardening-checklist: Minimum hardening per camera: unique 20+ character alphanumeric admin password (avoid @ : / % # which break RTSP URLs), a separate low-privilege stream user, P2P/UID/cloud/DDNS/UPnP/FTP/e-mail/SNMP/Telnet/SSH off, RTSP and web authentication on (Hikvision: digest/basic with MD5 digest algorithm for Frigate), firmware only from the vendor's own download page, and credentials injected into Frigate via FRIGATE_* environment variables instead of the YAML.
- [medium] bitrate-storage-math: 1 Mbps of continuous recording is 10.8 GB/day (decimal), so 4 cameras at 4 Mbps (typical 4-5MP H.265/H.264 main stream) consume 172.8 GB/day = 5.2 TB per 30 days continuous, 8 Mbps (4K-class) consumes 346 GB/day = 10.4 TB/30 d, and motion/person-only retention cuts that to roughly 10-40% of those figures.
- [medium] frigate-container-network-and-ports: Frigate in Docker bridge mode with ports published on 127.0.0.1 satisfies the house convention: its 8971 (authenticated UI/API), 8554 (RTSP restream) and 8555 (WebRTC) bind loopback only, while the unauthenticated port 5000 and go2rtc API should never be published beyond loopback.

- [high] api-recordings-delete-range: DELETE /api/recordings/start/{start}/end/{end}?cameras=a,b&keep=motion,object,audio (admin) unlinks every recording segment that overlaps the range - including segments only partly inside it - and deletes the matching DB rows, so it is the correct primitive for removing footage while keeping Frigate's database consistent.
- [high] api-reviews-delete-and-list: POST /api/reviews/delete {"ids":[...]} deletes the review rows AND every recording segment of that camera overlapping each review's [start,end] (including segments shared with an adjacent review), and GET /api/review exposes data.objects ('person' vs 'person-verified'), data.sub_labels and data.detections (event ids) but has no offset paging.
- [high] api-export-and-quarantine-copy: POST /api/export/{camera}/start/{start}/end/{end} with {"name":...,"source":"recordings"} queues a stream-copy export (HTTP 202 + export_id; 503 when 100 jobs are queued) saved under /media/frigate/exports, which retention never removes; exports are deleted only via POST /api/exports/delete {"ids":[...]}.
- [high] api-media-sync-and-db-consistency: Deleting recording files directly on disk leaves Frigate's database stale (usage stats can exceed 100%, playback of missing files fails), and POST /api/media/sync only removes orphans (dry_run defaults to true, aborts if >50% would be deleted) - it cannot re-adopt restored files - so all deletion should go through the API.
- [high] api-perception-interface: Frigate already exposes what the Claude-facing perception interface needs: GET /api/{camera}/latest.jpg (live snapshot), GET /api/events/{id}/snapshot.jpg, GET /api/events?in_progress=1&labels=person (who is on camera now), GET /api/stats, plus MQTT frigate/events, frigate/reviews and frigate/tracked_object_update (face name+score per attempt).

- [high] review-items-skip-stationary-people: Review items (and therefore alert/detection retention) only extend while an object is moving: objects with motionless_count >= detect.stationary.threshold (default 50 frames = 10 s at 5 fps) are ignored unless loitering, so a person sitting still at a desk is NOT covered by review windows, while the tracked-object event for that person keeps running.
- [high] face-recognition-pipeline: Frigate face recognition runs only on the low-resolution detect stream, only for tracked person objects with a detectable face, using small=FaceNet (CPU) or large=ArcFace (GPU), and publishes a sub_label only when the area-weighted running score across attempts reaches recognition_threshold (default 0.9).
- [high] recognition-propagates-per-track: A face recognition is attached to the tracked-object id, so one confident recognition labels the whole event (start to end, including frames where the face is not visible) and flows into Event.sub_label and ReviewSegment.data.sub_labels, but it does not propagate to other tracks or cameras.
- [high] face-attempt-budget-failure-mode: For each person track Frigate stops attempting recognition after 12 classified face crops without a label (or 6 more after one), so a track that burns its attempts on blurry/distant 'unknown' faces is permanently unrecognised even if Leo later walks up to the camera.

### RECOMMENDATION
Use Frigate 0.18.0, pinned as ghcr.io/blakeblackshear/frigate:0.18.0-tensorrt, in its own compose project with a Mosquitto sidecar. Do not run it privileged. Publish only 127.0.0.1:8971, and set tls.enabled False behind your Caddy gateway. Keep 5000, 8554, 8555 and 1984 unpublished. Add an egress default-deny for the Frigate container, and set telemetry.version_check False.

Pin the container to one GPU with the compose deploy reservation, using device_ids. Consider GPU0 so Frigate's CUDA context and VRAM stay off the compute GPU. Use preset-nvidia for decode and the onnx detector with a YOLOv9 ONNX model. First start will look stuck for about 10 s while sm_120 kernels JIT-compile. Watch for detection restart loops (PR #22685). I found no source that tests an RTX 5090 specifically. Frigate+ is not needed.

Replace the 'record everything, scrub daily' idea with Frigate's own retention. Set objects.track to person, set continuous and motion retention to 0 days, and keep only alerts with mode active_objects for a short window. Non-person footage then never leaves the tmpfs cache. I would not enable face recognition, since 'clips I'm in' equals 'clips with a person' for a single resident. Size storage as near-continuous, about 170-350 GB per day for 4 cameras at 4-8 Mbps.

Storage on ZFS:
- **Datasets:** create tank/frigate as an encryption root with raw-key encryption. Give recordings a child dataset with recordsize=1M, atime=off, a refquota and lz4. Put /config, the SQLite DB, clips and exports on an NVMe dataset with its own encryption root. Do not use mergerfs-style tiering.
- **Unlock and mount:** stock zfs-mount.service does not load keys, so write an unlock unit ordered before Docker. Use create_host_path: false on the recordings bind mount.
- **What encryption covers:** it only defends against pulled or discarded drives. Choose the key handling deliberately: a key file on the root filesystem, a TPM-sealed key, or a passphrase that needs a human after each reboot.
- **No snapshots:** exclude Frigate datasets from sanoid and syncoid, because snapshots preserve footage you deleted.
- **ZFS version:** check whether Ubuntu's OpenZFS 2.4.1 includes the 2.4.2 fix for read corruption after block clone plus truncate.

- **Event bridge:** write a small supervised bridge that subscribes to frigate/events, frigate/reviews and frigate/available. It should feed events.json/SSE with debounced TTS. Broker ACLs should limit it to read-only.
- **Presence:** treat camera person events as arrival/departure transitions. Derive 'away' only after no person has been seen for N minutes and the last zone was an exit. Fuse with mmWave or phone presence, because stationary people and blind spots break camera-only presence.
